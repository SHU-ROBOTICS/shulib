## 0. Why this chunk, why now, and what it is measured against

The team lead's direction (2026-09-18): *"I want the ability to make a bot without coding"* and
*"I want the main to be a LOT cleaner and human looking through our library."* Both are Phase G's
promise (master plan §17: Tier 0 zero-code hardware, Tier 1 data-driven auton), and **none of it is
built.** G1 is the foundation: the in-memory types a robot is described by, and the builder that
turns them into a wired, driving `Chassis`. G3's codegen will fill those types from a `.vexbot`;
R3d's calibrator already fills the drivetrain slice on the robot; a code-fluent team fills them in
C++. Three sources, ONE representation, ONE builder.

**The measure is `src/main.cpp`.** Today the library program's composition root is a fifty-line
struct that names every adapter, every seam and every constructor argument by hand
(`tanklib::TankRobot`, `src/main.cpp:604-670`), and the X-drive graph is a
second such struct (`Robot`, `src/main.cpp:335-424`). The DoD (build-order G1): **"a hand-built
config produces a working Chassis in two lines; zero VexBuilder dependency."** The target a
competition main converges on — names illustrative until this brief fixes them:

```text
shulib::hal::pros::ProsDevices devices;                          // the adapters, made on demand
shulib::robot::Robot robot{shulib::robot::build(config, devices)}; // the whole graph, wired
```

with `config` a `constexpr RobotConfig` typed by a person today and generated by G3 tomorrow, or a
`DrivetrainDescription` read off the SD card by R3d Part 2 dropped into it.

**Why it does not wait for the robot.** G1 is host-only by construction (Phase G preamble: "built
and tested against synthetic fixtures first"); the builder is proven on the plant through fakes,
exactly as every graph in the tree has been. Wiring it into `main.cpp` is its Part 2.

## 2. Scope

### Part 1 — IN (this brief): the types, the builder, the host proof

1. **`config/robot_config.hpp`** (new directory `include/shulib/config/`, PROS-free, allocation-free,
   fixed-width like the description so G3 can `constexpr` it):
   - `RobotIdentity{char name[32]; char team[16]; char season[16];}`.
   - `DrivetrainConfig` — a tagged choice: `Tank{hal::DrivetrainDescription description}` (the R3d
     representation, embedded, not copied field by field) | `XDrive{signed ports[4] in the F5 wheel
     order, cartridge, imuPort, driveRadius}` | `HDrive{…, strafe port}`. Tank is the only one the
     calibrator and the record produce; the holonomic two are typed by hand (spring) and exist so
     `main.cpp`'s X-drive graph can be expressed as data in Part 2. `kind()` accessor.
   - `OdometryConfig` — `DriveEncoders` (the default for a tank; needs nothing) | `TrackingWheels{
     forward{port, wheelDiameter, offset}, lateral{port, wheelDiameter, offset}}` (Pilons).
   - `SensorsConfig{gps{present, port, leverArmForward, leverArmLeft}; /* tags, vision: ABSENT in
     Part 1 — no adapters exist */}`.
   - `MechanismConfig[kMaxMechanisms]{name[24]; motor ports[4] signed + count; pneumatic ports[2] +
     count}` — **TYPES ONLY in Part 1** (so F7's schema is complete for G3); the builder constructs
     no mechanism here (G2/T3 consume them with the registry).
   - `TuningConfig` = `chassis::ChassisConfig` (gains/budgets; provisional).
   - `RobotConfig{identity, drivetrain, odometry, sensors, mechanisms[], mechanismCount, tuning}`
     with `valid(why, cap)` — every contradiction a typo produces (a port twice across drivetrain
     / pods / GPS / mechanisms; pods on a tank with `DriveEncoders` is fine, pods declared but
     `DriveEncoders` chosen is a warning not an error; a GPS lever arm non-finite; …) and
     `describe(buf, cap)`.
   - `IRobotConfig` — the seam: `virtual const RobotConfig& config() const noexcept = 0;` with
     `StaticRobotConfig` (holds one by value). Master plan decision #10's name, kept.
2. **`config/route.hpp`** — `Waypoint{x, y, heading; HeadingMode{Fixed, Free}; Motion{Start,
   MoveToPose, DriveTo, TurnTo, StrafeTo, Hold}; bool reverse; Constraints{maxLinear, maxAngular,
   timeout}; Marker markers[4]; markerCount}`, `Marker{char id[24]; int32 args[2]; argCount}` (typed
   args as the master plan sketches; `{id:"lift_to_level", args:{3}}`), `Route{char name[32];
   Waypoint waypoints[kMaxWaypoints = 32]; count; valid(why, cap)}`, `IRouteSource{virtual const
   Route* route(std::string_view name) const noexcept = 0; virtual std::size_t count() const;
   virtual const Route& at(i) const;}` with `StaticRoutes` over a caller's array. **Execution is
   G2's**; Part 1 pins the shape and its validity rules (a `Start` only at index 0; a `Hold` with a
   timeout; a marker id non-empty; no NaN anywhere).
3. **`hal/device_provider.hpp` — `IDeviceProvider`**: the ONE target-specific seam the builder
   needs. Devices BY PORT, constructed or looked up on demand, owned by the provider:
   `IMotor* motor(std::int8_t signedPort, MotorCartridge)`, `IImu* imu(port)`, `IGps* gps(port,
   leverFwd, leverLeft)`, `IRotation* rotation(port)`, plus the port-less ones `IClock& clock()`,
   `IBattery& battery()`, `ITelemetrySink& telemetry()`, `motion::ITickPacer& pacer()`. A device
   that cannot be made returns `nullptr` and `lastRefusal()` says why (the port); the builder turns
   that into a refusal naming the port — never a fake, never a null in the graph. **Part 1 ships
   `hal::fake::FakeDeviceProvider`** (host: hands out FakeMotor/FakeImu/FakeGps/FakeRotation from
   fixed storage by port, with hooks so a test can attach them to a `DrivePlant` as coupled members
   — the `CoupledMembers` rig's job, done once here). `ProsDeviceProvider` is **Part 2's**.
4. **`robot/robot.hpp` — `robot::Robot` and `robot::build()`**: `Robot` OWNS the PROS-free graph in
   construction order (a kinematics variant `{TankKinematics | MatrixKinematics}`, up to two
   `MotorGroup`s over provider-owned motors, one `DriveGeometry` per side, an odometry variant
   `{DriveEncoderOdometry | PilonsOdometry}`, `ComplementaryFusion`, the GPS corrector when a GPS is
   present, `Localizer`, `FaultLatch`, `HealthMonitor`, `RobotContext`, `MotionDeps`, `Chassis`;
   absent devices as the explicit `Absent*` objects) and BORROWS the devices from the provider.
   Non-copyable, non-movable, constructed in place (`static Robot r{…}` in a main; `std::optional
   <Robot>::emplace` in a test). `BuildVerdict validate(const RobotConfig&, IDeviceProvider&)` is
   a PURE pre-check (config validity + every device obtainable + the F5 wheel count matching the
   motor count) whose verdict names the failing port or field; `Robot` construction PRECONDITIONS
   on a passing verdict. `Robot::chassis()`, `::localizer()`, `::faults()`, `::health()`, `::context()`,
   `::describe(buf, cap)` (the banner line: identity + drivetrain source + geometry + which devices
   are present/absent). "Two lines" is `FakeDeviceProvider devices{…}; Robot robot{config, devices};`.
5. **The proof, on the plant:** a `RobotConfig` for a two-wheel tank (drive encoders) and one for
   the X-drive (tracking wheels + GPS) each produce a `Robot` whose `Chassis` drives the plant to a
   pose **bit-identically** to the longhand rigs (`chassis_facade_test`'s standalone case; the
   `GroupRig` of `motor_group_plant_test`) — the builder adds a way to wire, never a different
   physics.
6. Tests (§4), the DoD (§5), the documentation contract (§6).

### Part 2 — OUT of this brief (its own brief after Part 1): the robot side

per device, refusals recorded — the drive program's `Member` pattern generalized); `src/main.cpp`

### OUT (other chunks)

- Executing a `Route` (`PathRunner`, the command-id registry, the manifest, F8) → **G2**.
- Constructing mechanisms from `MechanismConfig` → **G2/T3** (with the registry that binds them).
- `.vexbot` parsing, codegen, `schemaVersion`, the SD loader, F7 → **G3**. `inferDrivetrain()` → G3.
- The `.shupaths` importer and the ten-minute guide → **G4**.
- Freezing anything. F7/F8 are G3/G2's; `RobotConfig`/`Route` grow additively until then.

### REJECTED

- **A builder that constructs PROS adapters itself.** The core is PROS-free by the CI guard; the
  provider seam is how the same builder serves the robot, the plant and a test — the F4 principle
  applied to construction.
- **Heap-owned graphs (`std::unique_ptr` everywhere).** The tree owns nothing on the heap in the
  control path; `Robot` is one in-place aggregate like `TankRobot`, sized by `kMaxSmartPorts`.
- **Redefining the drivetrain slice in `RobotConfig`.** R3d's description IS the tank slice; a
  second struct with the same fields is how a record and a config come to disagree.
- **A `Route` that carries code** (the legacy `code_template`): markers are ids + typed args; the
  binding is G2's registry (master plan §16.3, the keystone of the no-code story).

## 3. Rulings

**B1 — `RobotConfig` embeds `hal::DrivetrainDescription` for a tank, by value, unchanged.** One
representation, three sources (the calibrator, the typed table, G3's codegen). Rejected: a
"profile" struct mirroring it (drift by construction).

**B2 — The provider hands out devices by PORT and owns them; the builder never owns hardware.**
Because the F4 seams are references, ownership must sit somewhere that outlives the graph; the
provider is that somewhere on every target, and it is the only file that knows what a port is.

**B3 — `validate()` is pure and total; construction preconditions on it.** A robot that cannot be
built says which port or field before any object exists — the R3b refusal-at-boot rule, made
library. Rejected: a builder that returns `std::optional<Robot>` (a non-movable object cannot be
returned by value without guaranteed elision games the V5 toolchain should not be asked to play).

**B4 — Bit-identity to the longhand rigs is the acceptance test.** If the builder's graph and the
hand-wired graph disagree by one ulp on the plant, the builder has changed the physics or the order
of ticks; either is a defect, not a rounding note.

**B5 — `Route`'s vocabulary is the facade's verbs plus `Start`/`Hold`, and nothing the facade
cannot do today.** A waypoint that needs a verb the library lacks is a request for a library
feature, filed as such, not a silent no-op (G2 will WARN and skip unknown MARKER ids, per §16.3;
an unknown MOTION is invalid at `valid()`).

**B6 — Fixed capacities are stated constants**: 32 waypoints, 4 markers per waypoint, 8 mechanisms,
4 motors per mechanism. A route longer than that is two routes. Registered as design constants,
not hardware beliefs.

## 7. Landmines

1. **Construction ORDER is the physics.** The longhand graphs tick `localizer.update()` inside
   `Chassis::drive`, not in the builder; the builder constructs and never ticks. Test 5's
   bit-identity is the detector.
2. **`MotionDeps::validate()`'s wheel-count check is the ONLY thing standing between a config typo
   and an out-of-bounds span index on the hot path** (`motion.hpp:201-210`); the builder's
   `validate()` must make the same check BEFORE the deps exist, naming the config field.
3. **`Chassis` is non-movable; so is `Robot`.** No factory returning by value; construct in place.
4. **The X-drive's ports are INVENTED (HA-111)** — the config constant that reproduces them must
   carry the same label, or the builder launders an invention into "data".
5. **Absent ≠ null.** A missing GPS is `AbsentGps`, never a `nullptr` in `RobotContextConfig`
   (its preconditions throw on null — and that is right).
6. **No `std::string`, no `std::function`, no heap** in `config/`, `robot/`, `hal/device_provider.hpp`.
   The route and config types are `constexpr`-constructible so G3 can emit them as `inline constexpr`.
7. **Do not touch F6/F10 surfaces** (`chassis.hpp`, `routine.hpp`): the pins fail the build, and
   the builder needs nothing from them beyond construction.
8. **No hardware claim.** A `Robot` built from a config has driven a plant, not a robot.
